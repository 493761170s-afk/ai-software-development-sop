# Profile — Shared Platform / Cross-Product Capability

适用于被其他产品正式消费的服务、SDK、媒体/AI处理能力和基础平台；不是只要用了后端就自动加载。

## Stage 1–2：服务边界与责任

区分独立产品用户与平台消费者，登记实际消费者、Owner、数据/租户归属、接口用途、支持范围和不做事项。定义资源/配额/计费归属、服务目标与故障反馈；具体SLO等指标由项目确认，不由Profile代填。

## Stage 3–4：消费者合同

定义版本和兼容窗口、废弃/迁移策略、异步任务状态、幂等、取消/恢复、错误与限流。隔离租户/产品/任务、日志、缓存、产物与高耗时或失败任务，防止单个毒性任务拖垮全部消费者。明确监控、恢复、谁有权发起生产操作和消费者通知。

## Stage 5–8：跨项目变更

建立 Contract → 所有消费者 → 对应负责人/工作项/测试 的登记。Breaking change走双方SOT的CR和影响闭包；更新接口文档、客户端及迁移任务，取得受影响消费者负责人确认和必要独立重审后开发。提供方不能在自己的Tracker里直接替消费者批准或宣布Done。

兼容变化也需有兼容证据，不以字段“只是新增”认定无影响。发布前验证消费者合同测试、版本组合、错误/配额/数据隔离、回滚兼容，约定发布顺序和通知。缺少消费者资料则阻塞相关变更，不猜对方已兼容。

提供方采用级别较低时，对高风险或STRICT消费者依赖的边界至少执行STRICT对应控制；不要求整个提供方全部升级，但不能向下削弱消费者保证。
