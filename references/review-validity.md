# 基线有效性、影响范围与增量重审

本文件定义 Pre-Coding PASS 的适用范围；[独立审查 Skill](../utilities/independent-pre-coding-review/SKILL.md)定义审查过程。初次接入仍须全面审 Stage 1–5，不能用增量审查绕过首次完整审查。

## 两种基线不能混淆

**合同基线**：Stage 1–5 的批准内容。建立清单：资料 ID、权威路径、内容 hash/版本、需求/工作项 ID、外部设计版本/导出快照、Tracker结构快照。审查绑定该清单和源仓库提交。

**代码候选**：实现提交、构建摘要、配置/数据版本。它绑定测试证据，不要求每次代码提交都重审 Stage 1–5。

后续 HEAD 推进不自动使 Pre-Coding PASS 失效；须证明合同基线未改变、当前工作在批准范围内。审查报告、授权记录、测试结果和 Tracker 进度更新不纳入合同内容 hash，避免报告写入就使自己失效。修改工作项 Scope/AC/依赖/必测集合则不是单纯进度更新。

## 何时需要重审

实质变化：Scope/业务规则/AC/NFR、用户或调用行为、架构/数据/API/事件/安全/Provider/模型输出合同、WBS职责边界/功能依赖、必需测试标准、把未来需求拉入本期。先标旧 PASS 在受影响范围 INVALIDATED，再走 CR 和独立重审，不能改完后补签。

非实质变化：纯拼写/格式、负责人/执行进度、在既有 AC/测试策略下实现测试代码、同一批准功能内登记不改合同的缺陷修复子任务。记录差异及不改变语义的理由，Technical/QA Owner确认，不能仅由修改者自贴标签。改变测试期望/阈值须分清纠错和标准变更；纠错仍遵守 Stage 7 TEST_CORRECTION。

## 影响集合算法

1. 列出改动的来源 ID、旧/新版本及语义差异，禁止只看文件路径或行数。
2. 沿双向追溯关系找需求/规则/AC → 设计 → 技术合同 → 所有直接/间接消费者 → Work Items → Tests/Eval → 配置/迁移/发布。共享 Auth/Tenant/Schema/API/Prompt/Provider 改动默认包含全部消费者，直到有证据排除。
3. 纳入数据读写方、继承权限、缓存/日志/队列、模型/提示配置及外部项目；沿依赖反复展开到不再新增。无法辨认的消费者记 UNKNOWN，不得当无影响。
4. 生成 `AFFECTED_IDS`、`EXCLUDED_IDS`及逐项排除依据、尚未定位的范围、图/搜索证据。Technical Owner负责闭包，QA Owner确认测试影响；共享接口还需消费者 Owner确认。
5. 阻塞受影响工作及未明确排除的消费者。独立 Reviewer核验闭包；只有有证据且被确认排除的工作可以沿有效旧 PASS 继续，不允许执行者单方缩小影响范围。

## FULL 与 DELTA

- FULL：首次项目/本期完整基线；缺少有效父审查；重大目标/架构变化；追溯不全、影响无法封闭，或 Reviewer不能核验旧证据。读取目标基线完整 Stage 1–5，不把未知范围默认为局部。
- DELTA：存在可验证的完整父审查，提供旧/新清单、语义 diff、完整影响闭包、排除证据、所有旧 Finding 状态；审全部受影响合同、消费者和测试以及与未变部分的交界。不只是看代码 diff。
- 上轮全面审查为 FAIL：可增量复审已关闭 Finding 和关联影响，但必须继承全量未决 Findings；仅当全部 BLOCKER/MAJOR清零才产生首次 PASS。
- 关键资料不可读时不给 PASS；恢复资料或升级审查范围。跨项目资料不可得不是 N/A。

新报告记录父报告、审查模式、适用 IDs/基线、保留/失效的旧结论。DELTA 不重写原报告、不伪造“全项目重新通过”。Figma/Jira 无不可变版本接口时导出可核验快照并记时间/hash；仅一个可变化 URL 不够。

## 通过与恢复

独立 Reviewer 明确新 PASS 和覆盖范围，Owner核验记录后恢复相应工作授权。FAIL、证据缺失或范围未知保持阻塞。普通任务只核验相关基线与现有结论，不全仓重扫。
