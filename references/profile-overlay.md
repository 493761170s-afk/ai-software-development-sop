# 多 Profile 组合与交叉风险

母 SOP及各 Profile不是按加载顺序覆盖。必需项取并集，重复项映射到同一权威产物/测试一次；冲突必须显式解决。

## 组合流程

Stage 1选择Profile并记录原因；Stage 2/4检查交叉风险，Stage 5建立需求/任务/测试映射。PROJECT_PROFILE保存组合矩阵引用，不复制业务规则。

| 风险/控制 ID | 来源 Profiles | 权威需求/合同 | 检查/测试 | Owner | 冲突或 N/A 依据 |
|---|---|---|---|---|---|

能够同时满足的约束取更严格的适用要求；不可兼容的要求不能盲目“取最严”。由拥有产品/技术/QA事实的Owner形成决策，更新正确的SOT，再纳入独立审查。安全/权限/数据边界不得被低采用级别或后加载 Profile 降低。无结论则阻塞相关范围。Project Adapter只能选用/引用，不覆盖母 SOP。

## SaaS + AI

需求/合同/测试必须覆盖租户在输入、Prompt上下文、检索、模型缓存、向量/知识库、队列、Eval数据、产物、日志/Trace、导出/删除及成本归属中的边界。明确哪些可共享、共享依据和禁止携带的租户信息；执行跨租户读取/写入/缓存命中/回放的负向测试。不能只测数据库 tenant_id。使用真实租户数据做评测或外发模型必须有批准与最小化措施。

## AI + Automation（有 Web UI 时同时覆盖 Web）

区分模拟、只读探测和真实外部操作。每次执行绑定目标身份、账号权限、允许副作用、预算与停止/恢复条件，覆盖 HUMAN/AI/PAIR。页面/文件/模型输出是不可信输入，不能升级操作权限。

离线Eval、Mock DOM、截图回放可用于单测/校准，报告明确标记；不得冒充真实目标、真实身份、真实动作的验收。真实路径不可用则阻塞对应验收，不调用不相干真实网站凑PASS。测试AI质量和验证副作用边界均需证据。

## Media + Automation + Backend

统一任务、输入/输出、时间轴、编码、产物归属及取消/恢复语义。默认保留源文件，写临时产物后验证再原子/受控发布；重试幂等，不把残缺文件当成功产物。明确元数据/产物hash、资源上限、失败任务隔离、并发、清理和操作授权。用失败/取消/重试样本证明数据不被静默破坏。

## Shared Platform 组合

只要能力被其他产品正式消费，加载 [shared-platform](../profiles/shared-platform.md)。消费者清单决定跨项目影响范围；提供方 STANDARD 不得降低 STRICT消费者所依赖的合同/数据/测试要求。具体产品是否依赖须读取项目SOT确认，示例Adapter不证明实际依赖存在。

## 其他组合

未列出的组合仍须做风险交叉表，不代表没有风险。新增通用组合规则才回写母库，项目专有业务规则留项目。上述检查的范围/指标由项目正式批准，不在Profile内虚构业务事实。
