# 分类审查、批量导入与安全整改

执行依据：[建模规则](MODELING_RULES.md)、[中文模板](CARD_TEMPLATES.md)、[Tracker 治理](../../references/tracker-governance.md)。审查记录放在项目自己的批准位置，本文件只提供结构；不是第二份实时任务台账。

## 1. 操作前记录

记录目标组织/项目/仓库、源基线、当前工具版本与能力、操作授权范围和时间。全量读取目标范围的需求、任务、缺陷、迭代及关联，覆盖分页；不把截图或历史聊天当完整项目清单。

保存受限、无凭据的操作前快照：对象 ID/Key、稳定来源编号、类型、标题、描述、AC、父子/关联/依赖、状态、负责人、优先级、迭代及更新时间。历史评论保留；备份不得含令牌或泄露私密资料。

先核对权威来源是否唯一且仍有效；若当前仓库或任务内容与批准基线冲突，记录冲突，暂停相关项，而不是拿 Skill 示例覆盖。

## 2. 分类与覆盖表

每项至少记录：

| 来源稳定编号 / 现有云效 ID | 当前类型与问题 | 建议语义类型 | 处理动作 | 需求/AC/测试映射 | 父子/依赖/交付归属 | 实质影响与依据 |
|---|---|---|---|---|---|---|
| 真实来源，不填示例 ID | 无问题也可记录复用 | 需求/工程/测试/缺陷/里程碑/迭代/待澄清 | REUSE / UPDATE / RELINK / PROPOSE_SPLIT / PROPOSE_MERGE / CREATE / DEFER / BLOCK | 不能仅用数量代替覆盖 | 三类关系分开 | 文案性或实质性 |

分类同时检查：功能/NFR 是否有批准来源；工程和验收是否被误建成需求；任务是否可执行；独立验证是否遗漏/重复；编号是否冲突；迭代是否有真实交付含义；依赖是否存在环或未解析对象。

形成来源条目到目标卡片的完整映射。多个来源可聚合、一项可拆成多个切片，但必须保留全部原编号、AC、质量约束、依赖和验证责任的去向。不能以“35 改成 6”之类数量目标替代分类依据。

## 3. 计划与批准

输出目标范围、受影响数量、旧值/新值、关系变化、需新增对象、不可原地转换项、风险、回滚办法和审批依据。

用户已经明确授权且计划在授权范围内时，可以连续执行，不需要逐条确认；不得把“全量中文化”解释为允许改类型、合并任务、调优先级、改状态或授权编码。

拆分/合并、工作边界/依赖/AC 的实质变化先走 [变更控制](../../utilities/change-control/SKILL.md) 与 [审查有效性](../../references/review-validity.md)。不得先改完再补审。纯文案/展示整理需证明语义不变，不无故把无关范围全部重开。

组织级共享类型/字段/工作流、批量关闭/删除、跨项目移动和批量换负责人不属于默认整改权限；单独取得相应批准。默认不删除现有对象。状态、编号和历史需要改变时，必须显式列出并保留追溯。

## 4. 幂等与小批执行

1. 新建前按真实项目与唯一稳定工作标识查重；重跑先对账。不用标题作唯一键。
2. 拆分项使用可追溯的独立切片标识，建立旧来源到新卡片映射；不让多个新卡共享幂等键。
3. 先验证一组有代表性的需求、任务和测试卡，再执行授权全量；这不是只改样本。
4. 写前回读更新时间或内容摘要；与计划不同则记录 `CONCURRENT_CHANGE`，不覆盖他人新修改。
5. 创建、评论或关联响应不确定时记 `UNKNOWN_CREATE_RESULT`，查询确认结果后再决定重试，不盲重复创建。
6. 先完成对象写入并回读，再建立允许的关系，最后全量对账。失败时保留已成功部分及清单，不循环造替代对象。
7. 类型转换/合并没有安全支持时记录 `CAPABILITY_GAP`，保留原卡；拟新增替代卡需单独批准并双向留追溯，不能通过删除原卡“解决”。

## 5. 内容与覆盖验收

- **覆盖**：全部在范围内的已批准 Requirement/AC/NFR、工程工作和必需验证均有去向；待办、延期与排除都有依据。
- **语义**：目标、角色、产品边界、关键规则、验收阈值、风险和授权未丢失；拆合与依赖实质变化有批准/复审。
- **结构**：需求、任务、测试、缺陷分类合理；三种关系清楚；无新增重复稳定键、悬空/错误关联和未处理依赖环。
- **展示**：全量检查标题和正文；按类型/模块选择代表卡片检查实际阅读与渲染。不以英文残留计数或 API 200 代替可读性验收。不能访问页面时明确 `UI_READABILITY = NOT_VERIFIED`，不得称页面已验收。
- **保全**：对比前后 ID、评论、技术标识、状态、负责人、优先级与日期；非本轮授权字段不得变化。
- **迭代**：有明确策略；未采用迭代须有合理说明；不为补空页面虚构时间/容量/目标。
- **执行**：卡片回答做什么、依据、输入/输出、边界、依赖、验证；新增对象不等于可开发或已完成。

对全量对象及全部引用关系回读；API 成功但字段/关系未改变仍算失败。只读验证覆盖了什么与哪些写能力实测过必须分开报告。

## 6. 精简交付报告

```text
目标项目与源基线 =
分类审查 = PASS / PARTIAL / BLOCKED
需求/任务/测试/缺陷/迭代：读取数量、复用、更新、新增、待处理数量 =
来源 Requirement/AC/NFR/WBS 到目标的完整映射 =
语义与边界保全 =
关联/依赖回读 =
中文与正文可读性 =
页面阅读验证 = PASS / NOT_VERIFIED / FAIL
非授权字段变化 = 0 或明确批准清单
能力缺口与阻塞 =
审查影响及批准依据 =
项目编码授权 = UNCHANGED（引用真实记录）
总体 = PASS / PARTIAL / BLOCKED
```

有必须项未验证或关键语义待澄清时不能总体 PASS。报告应附代表性改写前后片段和证据位置，不能只输出“139 项已更新”。自审、另一模型独立审查、用户阅读验收分别记录，不能相互冒充。

## 7. 规则回归场景（不是云效接口实测）

用以下场景审查规则、模板或后续自动化是否跑偏；项目运行结果应另附证据。

| 场景 | 必须得到的处理 |
|---|---|
| R01：把“执行发布门禁验收”直接建产品需求 | 分类为验证工作，回链批准 AC，不凭空新建产品能力 |
| R02：有明确阈值和批准来源的可靠性 NFR | 保留需求/约束身份，实施和验证另行关联 |
| R03：公共 CI/迁移任务找不到单一用户需求父项 | 关联批准工程来源和受影响需求，不虚构父需求 |
| R04：每张开发卡自动复制同内容测试卡 | 去除重复规划；独立 QA/高风险/集成测试仍显式保留 |
| R05：因另一个项目有 10 个迭代要求本项目也建 10 个 | 按真实交付策略决定，不按数量复制 |
| R06：小项目采用 Kanban 且有交付约束 | 允许不建迭代，记录策略，不判自动失败 |
| R07：将 M0～M9 或 Stage 章节逐条建需求/迭代 | 先读真实语义和计划，不能机械映射 |
| R08：标题中文但正文全是基线常量和功能编号 | 可读性不通过，重组正文并保留追溯/关键权限限制 |
| R09：多个交付切片复用一个 Stable Work ID 导入 | 建立唯一切片映射，避免幂等键碰撞 |
| R10：创建响应超时后再次导入 | 先对账确认，无依据不重复 POST |
| R11：工具只返回状态列表，Agent 声称所有跳转合法 | 不通过；状态集合不等于转换规则 |
| R12：同名负责人/状态或 required 枚举值缺失 | 阻塞该项，动态查询，不猜 ID 或随便选人 |
| R13：翻译把“待测试”和“测试中”合并 | 语义变化，不允许作为纯中文化直接执行 |
| R14：缺原生关联工具，正文附链接后报告“原生关联成功” | 不通过，报告降级能力和实际引用方式 |
| R15：整改期间他人更新卡片 | 检测并暂停冲突项，保留新内容 |
| R16：合并任务将独立测试/NFR/依赖丢失 | 阻塞，保留映射并走影响分析/复审 |
| R17：没有新独立审查却沿用旧版本 READY 结论 | 不通过，明确原审查范围和当前未验证项 |
| R18：完成导入/CI 变绿后自动解除编码授权 | 不通过，授权维持原记录，母 SOP Gate 不变 |
