# 云效需求、任务、缺陷与迭代建模规则

规则入口：[云效适配器](SKILL.md)。执行前读项目当前正式需求、WBS、技术合同、测试计划和 Tracker；不得根据标题猜产品方向。

## 1. 先分类，再建卡

| 对象 | 应回答的问题 | 不应直接充当该对象的内容 |
|---|---|---|
| 需求 | 谁在什么场景下，需要得到什么能力或结果，怎样验收？ | 文档章节、接口清单、开发步骤、纯测试执行清单 |
| 大需求/能力分组（可选） | 哪些需求共同支持一个可解释的业务目标？ | 为凑层级创建的空壳、把每个里程碑变成产品需求 |
| 开发/工程任务 | 为已批准能力或工程约束交付什么具体成果，怎样独立验证？ | “完成整个系统”、只有功能编号、重复粘贴整个规格 |
| 测试/验收任务 | 独立验证哪些 AC、风险或集成行为，交付什么证据？ | 把每条测试断言建成产品需求，或与开发卡重复记录同一次自测 |
| 缺陷 | 在哪个已实现候选和环境中，实际表现如何偏离哪条批准标准？ | 尚未实现的计划功能、新想法、未决产品规则、一般工具配置缺口 |
| 迭代 | 在一次交付周期内完成哪些目标与工作，如何进入和结束？ | Stage 文档章节、任意模块目录、无交付约定的 M0～M9 标签 |
| 里程碑/发布目标 | 哪个阶段性结果达到后算通过一个计划节点？ | 自动等同固定时长迭代，或重复生成为需求与任务 |

技术型项目的使用者可以是开发者、管理员、外部调用方或运维人员，不要求每条需求都有终端用户界面。

## 2. 需求：能力和约束，不是工程操作目录

需求写清背景、受益对象、目标、范围、关键流程/例外与可观察 AC。命名使用“用户能够……”“系统在……时……”或清楚的能力名称，不能只剩模块缩写。

安全、隔离、可靠性、成本等 **NFR 可以是真需求**：只要是项目批准的可验收产品/系统约束，就保留其需求身份和追溯。不能把所有技术内容都降为任务。判断依据是条目表达的内容，不是标题里有没有“验收”二字。

示例均为分类示意，只有项目已批准相应标准才可采用：

- “外部服务超时后，用户能看到失败原因，且同一请求不被重复计费”：可验收需求/质量约束。
- “执行外部服务超时、限流和计费回归，并提交报告”：测试任务。
- “实现失败分类、幂等记录与调用日志”：工程任务。

一个宽泛条目同时包含约束、实现和验收动作时，将三类内容分别映射、互相引用；保留原 AC/NFR，不凭空添加重试、降级、自动发布等未批准能力。

每个来源 Requirement/AC 可映射到一张或多张合理卡片；不要求每个原文小节都新建需求。一个需求也可由多个已批准条目共同支撑。数量必须由范围和交付边界解释，不以“需求越少越好”或“与另一个项目数量相同”为目标。

## 3. 任务：可执行交付切片

一张任务应有一个主要目标、明确输入/输出、责任人、边界、依赖和完成证据。可以按前端、后端、数据、安全、媒体、运维、文档等角色/模块拆，也可以按端到端行为拆；不强制每个需求都复制相同的前后端任务套装。

优先形成可独立 Review 的交付，一张任务通常可对应一个 MR；必要时可以多个 MR 或无代码交付，但要说明成果和验证方式。禁止把“一卡一个 MR”当绝对条件，也禁止十分钟级按钮微任务或整模块含糊大任务。

工程基础、安全加固、公共契约、CI、跨需求工作可直接作为工程任务，关联批准的工程/NFR/架构来源以及受影响需求。不必为了挂父项虚构“用户需求”。无法引用有效批准来源则先澄清，不自动开发。

每张任务只摘录其实际相关的功能编号、Figma 页面/节点、合同与 AC。不要把全部 CT/Feature 列表、整页 UI 规格或通用系统声明塞进每张卡。共同背景链接到唯一来源；局部完成标准必须在卡上可直接理解。

原 WBS 一项需要拆为多个交付切片时，先形成可追溯子项标识及拆分映射。不能让不同切片共享同一个幂等键，也不能仅靠标题变化重新编号并重复建卡。

## 4. 测试、验收、缺陷与未决事项

每张开发任务必须明确必测集合和完成证据，但**不是每张开发任务都机械再建一张测试任务**。以下工作值得独立建卡：跨模块集成、端到端场景、重大风险、独立 QA/回归、发布验收及有独立责任人/交付物的验证。开发自测是开发任务自身交付的一部分；独立测试责任不能因此取消。

共享测试任务可以覆盖多个需求，但必须列清对应 AC、环境和交付证据。所有必需 AC 都要有明确验证责任，不得通过合并任务丢失覆盖。测试用例、测试执行和测试任务不互相替代；项目使用 Testhub 时，以关联引用减少重复，不另造平行进度账本。

缺陷至少记录严重程度、优先级、环境/候选、复现步骤、预期/实际结果、批准标准来源、证据、处理人与复核安排。关联任务和相关 PR/MR、Commit：尚无修复提交时明确“待修复后补”，不编造 URL。Severity 和 Priority 是不同维度；值、字段 ID 和用户 ID 依据真实配置解析。

新功能、范围调整或验收标准变化进入需求/变更控制。阻塞项和风险记录实际影响，不为了统计 Bug 数量把每次鉴权/配置失败都登记成产品缺陷；产品本身违反已有约定时再按缺陷处理。

## 5. 三种关系分开管理

```text
需求/能力 —— 分解关系 —— 开发或测试任务
任务/缺陷 —— 依赖关系 —— 前置任务、契约或外部条件
需求/任务/缺陷 —— 交付归属 —— 迭代、里程碑或发布目标
```

迭代是排期/交付维度，不是所有需求和缺陷的强制父节点。不要把“迭代 → 需求 → 任务 → 缺陷”当成平台强制树。缺陷通常关联需求/任务，不必是任务子项；一张任务可关联多个需求。实际父子类型和多关联能力由项目配置决定。

优先使用平台实际支持的原生关系；不支持时，在同一 Tracker 明确记录结构化关联/依赖并声明能力损失。描述中写“关联了”不算证明，必须回读；URL 引用不能冒充原生关系。

依赖应说明“必须等待什么结果”，区分代码未完成与契约已冻结可并行。禁止只靠 M 编号判断前后置。验收时检查环、悬空关联、未解析前置与共享工作被遗漏的消费者。

## 6. 迭代与里程碑

项目必须选择并解释策略：`ITERATION_MODE = TIMEBOXED | DELIVERY_BATCH | KANBAN`。

- `TIMEBOXED`：有批准的目标、工作集合、起止时间和容量依据。
- `DELIVERY_BATCH`：按小批交付组织，有明确进入/结束条件；尚无批准日期时标记待排期，不编造日期，不伪称时间盒。
- `KANBAN`：持续流动或小范围单次交付可以暂不建迭代；记录“不使用迭代”的理由、交付优先顺序、在制品约束和发布验收方式。

M0～M9 可能是工程里程碑，不是 SOP Stage 1～5，也不天然等于迭代。保留已有稳定编号及批准计划；只有实际符合上述交付策略时才映射为迭代。仅为清空“迭代”页面或看起来统一而创建占位迭代不合格。

默认规划近期可执行批次和后续待办，不强制把全部需求预排到十个迭代，也不强制删除已有合理安排。没有迭代并不自动不合格；有十个迭代也不自动完备。应审查交付目标、依赖和结束条件。

## 7. 中文内容与可读性

用户可见标题、摘要、正文、验收、迭代名称和新增交付评论默认中文。保留真实编号、路径、URL、SHA、命令、API/字段/枚举/代码符号；必要术语先写中文解释。已有明确中文名称时优先中文，接口中的技术名称保持原样。

标题表达一个能力或动作；可以有一个简短类型前缀，如“【后端】记录调用成本”。原稳定编号需保留追溯，但不必把全部编号和缩写放进标题。机器字段与长基线声明移到文末“来源与执行约束”，不删权限、预算和安全限制。

卡片首屏应能回答：谁需要它、要做什么、交付什么、如何验收、有什么重要限制。没有编码授权时仍应有简短醒目提示，例如“计划项；未获得编码授权”，不能只藏在链接后。

使用正常标题、段落、列表和可点击链接。只有命令/代码/配置放代码块；禁止把整篇说明裹成等宽代码块。前端未正确渲染时记录格式问题并按支持的描述格式修正，不能仅统计英文字母就宣称中文化成功。

**英文标题残留为零不等于可读性通过。** 必须读列表和代表卡片的完整正文；标题中文但正文仍是“权威声明 + 全量编号 + 拼贴规格”同样不通过。历史评论属于审计记录，不批量覆写；需要更正时新增中文说明。

## 8. 不改变产品方向的整改

分类、翻译与排版不是新增功能的授权。不能借整理卡片删除 NFR/AC、合并掉独立测试、放宽门禁、修改优先级、状态、日期、负责人或依赖。确需改变这些项时，单列变更、范围和批准依据。

字段/状态显示名可能属于组织共享配置；项目级整改不得越权修改它们来影响其他项目。类型无法原地变更时，先记录限制与替代方案；不得默认删除原卡重建。涉及工作边界、依赖或验收语义的实质重分类需按母 SOP 做影响分析和相应复审。
