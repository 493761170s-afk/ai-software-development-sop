# 云效项目协作适配器

## 适用与权威

当项目使用或准备采用云效 Projex，创建、导入、中文化、重分类、调整层级或批量更新工作项前，必须读取本适配器。日常执行按项目已批准的映射和最小读取集处理，不必每次重审全项目。

本适配器属于 [母 SOP](../../SKILL.md)，不是第二套研发流程。生命周期、授权和独立审查仍由母 SOP 及其专项规则拥有。项目产品范围、需求、接口、数据库、Figma、优先级和排期以项目当前正式资料为准，不能从其他项目或本适配器示例推导。

## 阅读顺序

1. [建模规则](MODELING_RULES.md)：先判断内容应放在哪里。
2. [中文卡片模板](CARD_TEMPLATES.md)：再组织用户实际阅读的内容。
3. [分类审查与安全整改](CLASSIFICATION_AUDIT.md)：生成计划、执行、全量回读和验收。

统一的是对象语义、追溯和阅读体验，不是需求数量、任务数量、迭代数量或同一套工作流名称。不能让所有项目机械复制一个示范项目。

## 执行路径

```text
读取项目身份、当前正式资料和已有工作项
→ 查询当前工具、权限、类型、字段、选项、工作流、成员、关系与迭代配置
→ 分类审查和来源覆盖检查
→ 形成变更计划并核对授权
→ 小批次验证，再执行已授权范围
→ 全量回读、语义/关系/可读性检查
→ 回写项目映射与证据
```

创建或批量整改前，分类审查必须有明确结论。`UNKNOWN`、来源冲突、类型歧义或关联写入能力未确认时，不得靠猜测补齐。先使用现有有效任务；禁止删库重建式整改。

## 项目接入记录

在项目自己的 `PROJECT_PROFILE` 或其引用文件中记录以下内容，不把实例事实写进本公共 Skill：

- 组织、项目、仓库的真实绑定及目标范围；唯一 Live Tracker。
- 需求、设计、技术合同和代码的各自权威来源、基线与允许的同步方向。
- 当前验证可用的访问方式、工具/服务版本、启动入口和工具筛选；凭据只记录安全引用，不保存值。
- 类型、字段、选项、负责人、状态、关联能力的实际映射与发现时间；缺口和替代办法。
- 工作项稳定编号与云效编号映射；迭代策略及分类审查记录位置。
- 人类责任人、执行者、复核者、可执行操作/预算、审查和授权证据位置。

未配置原生字段时，可使用同一个 Live Tracker 卡片内的结构化中文栏目承载；不得另建持续维护状态的本地数据库或 Markdown 任务台账。静态映射、导入计划与审计快照不承担实时进度管理。

## 工具与权限：先探测，不猜接口

区分四件事：客户端是否加载工具、工具是否被 toolset 筛选、PAT/账号是否有权限、服务端资源是否已配置。工具缺失不是权限不足；有工具不代表写操作成功；接口报错也不能单凭状态码断定客户端有缺陷。

使用项目已验证的访问路径。可以是原生 MCP，也可以是 Linux shell 调 `mcporter` 和已安装 wrapper；某客户端失败时，只对该客户端记录限制，不把它写成所有项目永久禁用原生 MCP。不要在公共规则中固定某台服务器路径、账号或令牌。

当前 MCP 未暴露某项操作时，先 fresh 读取工具清单与 schema，再查云效当前官方 OpenAPI；有授权且接口适用才补调用，否则记录 `CAPABILITY_GAP` 或交给人工。不能把在卡片里写一个 URL 宣称为原生双向关联成功。

读取全量列表必须覆盖分页。创建前校验全部必填字段与真实枚举值；负责人必须是可解析的实际成员，不能默认为任意用户。同名对象、同名状态或选项歧义时停止该项。写后回读验证目标值与关系。

只允许在经过发现和校验的项目映射中保存真实 ID；禁止在公共 Skill 或程序逻辑中写死“待测试 = 某 ID”。状态列表不等于完整允许转换图；服务端流转规则与角色限制仍须尊重。

凭据不得进入源码、普通配置、命令参数、聊天、截图或调试日志。优先环境变量或 secret store；项目若批准专用受限凭据文件，也必须位于仓库外、限制权限且不输出其内容。密钥泄露应撤销并轮换，不继续测试旧凭据。

## Codex / Gemini / 人工的日常执行

- 先读取真实任务、依赖、批准基线、当前状态和授权；未获开发授权时，不因卡片存在或显示“可开发”就开始编码。
- 在允许的真实状态图内更新进度；待测试、测试中、已完成不能混为一个语义。缺陷的重复/无法复现/不修复按项目实际状态或解决方式映射，不凭空创建状态。
- 代码变更关联真实 PR/MR、提交 SHA；CI 和重测试记录准确的运行 ID、环境、候选和日志。确认实际运行了要求的命令，不能仅凭流水线模板创建成功或空任务变绿判定测试通过。
- 实现偏离批准标准时记录缺陷；范围或标准变更走变更控制。回归和验收遵守母 SOP，不把修复者自测、MR 合并或 Flow 成功当作自动关闭依据。
- 复核者只能在授权范围内写审查结论；独立审查默认只读，不自改被审对象、不代签人类批准。是否构成独立模型按母 SOP 的真实来源规则判断。
- 可以连续执行获准的任务集合；危险批量操作仍按审查计划授权，不因“免交互”关闭安全边界。状态写入失败时保留事实证据并对账，不重复执行代码或伪称已同步。

## GitHub 与 Codeup 的边界

平台分工由项目明确选择，不强制迁库。采用“GitHub 规划、Codeup 开发”的项目必须记录冻结文档基线及生效顺序：GitHub 的草稿变更不自动成为当前开发依据；批准并审查后，以限定文档路径的差异在 Codeup 提交 MR，再更新相关 Projex 任务与基线。

禁止在 Codeup 已有新开发后用 GitHub 整仓强制镜像覆盖代码。禁止把 `AGENTS.md`、Skill、CI、迁移脚本当成普通文案自动覆盖；它们可能改变权限和流程，需要单独核对。方向、AC、合同、依赖或工作边界的实质变化按母 SOP 使受影响审查失效并复审。
